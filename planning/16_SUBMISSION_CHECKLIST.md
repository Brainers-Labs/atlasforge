## 1. Working artefact
- [ ] Public GitHub repo, tag `v0.1.0`. **The repository is public** (`Brainers-Labs/atlasforge`) and a release is tagged, but it is `v0.1.0a2`, a pre-alpha — not `v0.1.0`. The alpha was published first on purpose: an upload to PyPI is permanent and a version's metadata cannot be edited, so the release had to carry the corrected URLs before it went out rather than after.
- [ ] `pip install brainers-atlasforge` works from PyPI in a fresh venv (Linux, macOS, Windows). **Not `pip install atlasforge`** — that name is an unrelated bioinformatics project; the import name and the `atlasforge` command are unchanged. **Partly verified:** on Windows a clean venv installed `0.1.0a2` from PyPI, `atlasforge --version` printed it and `import atlasforge` worked; CI installs the built wheel and sdist into clean venvs on Linux, but from `dist/`, not from the index. No PyPI download has been exercised on macOS. `--pre` is not required while the alpha is the only version published — pip falls back to pre-releases when there is no stable release to prefer.
- [ ] `doctor`, `run`, `transcribe`, `eval`, `compare` work against real N-ATLaS
- [x] Example reports committed under `examples/reports/` — `report.{md,json,html}` and `comparison.{md,json,html}`, all synthetic. `tests/unit/test_examples.py` regenerates them from the current code and fails if a byte differs, so they cannot describe an older version of the tool.
- [ ] Colab notebook(s) run top-to-bottom. Written (`notebooks/atlasforge-quickstart.ipynb`, offline demo path) and its portable cells are executed by `tests/unit/test_notebook.py`; **nobody has opened it in Colab and run it there yet**

## 4. Technical documentation
- [x] Docs site live: quickstart (A/B paths), licences & access, guides (eval, compare, ASR, fine-tune, vLLM), CLI & API reference, dataset format, metrics & normalization, troubleshooting. **Live at https://brainers-labs.github.io/atlasforge/**, deployed by `.github/workflows/docs.yml` on every push to `main`. Every page builds strictly (`mkdocs build --strict`), and the deploy job runs only after that build succeeds, so a broken link cannot reach the site — it stops the update instead. The Python API and CLI reference pages are generated from the code at build time, so they cannot describe an older version of the tool.
